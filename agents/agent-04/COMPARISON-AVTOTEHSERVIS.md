# Сравнение приёма заявок: kadry-pro (после PR #8) ↔ avtotehservis

Референс: `sledovatel61/avtotehservis`, рабочая продовая реализация приёма
заявок (relay → Telegram + почта). Секреты, токены, chat ID и адреса
получателей Автотехсервиса сюда НЕ переносились и переноситься не должны:
заявки Марии идут только ей. Сам Автотехсервис не изменялся.

## 1. Сводная таблица

## 2. Риск ложного успеха и дублей (в т.ч. мобильное автозаполнение)

**Ложный успех.** В avtotehservis риск ВЫСОКИЙ и системный: honeypot и
too-fast отвечают `201` с талоном без доставки, а клиент показывает обычный
экран успеха — это точный сценарий K-1123 (на kadry-pro он мигрировал именно
отсюда). В kadry-pro после PR #8 риск НИЗКИЙ:
1. автозаполнение в офскрин-ловушку (`company_website`, `left:-9999px`) —
   доставляется с пометкой (закрыто, регрессионные тесты);
2. слишком быстрая отправка — доставляется с пометкой (закрыто);
3. остаточный случай: агрессивный менеджер паролей, заполняющий даже
   `display:none`-ловушку (`_gotcha`) — заявка считается ботом и НЕ
   доставляется, но экран честный: «подтверждения доставки нет» + телефон.
   Полностью убрать потерю можно только переходом на «доставлять всё с
   пометкой» (спам будет доходить до Марии с флагом) — это решение владельца;
   рекомендация — оставить как есть: сообщение даёт человеку шанс позвонить.

**Дубли при повторе.** Оба проекта безопасны: ключ идемпотентности живёт от
первой попытки до успеха; повтор после таймаута получает `duplicate:true` без
повторной доставки (kadry-pro к тому же честно пишет «возможно, заявка уже
ушла; повтор безопасен — дублей не будет»). Новый ключ выдаётся только после
успеха. Фикс 409 в этой ветке дублей не создаёт: повтор с новым ключом
происходит только когда данные формы ДРУГИЕ (иначе сервер ответил бы
`duplicate:true`, а не 409) — значит это законная новая заявка.

## 3. Что проверено кодом, а что — нет

*Проверено кодом и тестами* (site 145/145, relay 44/44, tsc/typecheck,
сборка, гейты): механика ловушек, honest-тексты, идемпотентность, таймауты,
возврат лимита, обработчик 409, отсутствие дубля обработчиков.
*Проверено на живом сервисе*: `/health` воркера (ok, telegram:true,
email:resend) и успешные workflow после PR #8. **Это НЕ доказывает доставку
заявки.** Доставка подтверждается только сообщением Марии — отдельно Telegram
и отдельно почта.

## 4. Крупное — передать Агенту 03 / на решение владельца

1. Хранение заявок + админка (как в avtotehservis: `lead_id`, список лидов) —
   защита от «пропало из бота» принципиально: заявка остаётся в базе.
2. Кнопка «Повторить» с таймером обратного отсчёта после 429 (UX референса).
3. Вложения (фото документов) — если Марии нужно.
4. Дизайн-решение: доставлять ли `display:none`-заполненные ловушки с пометкой
   вместо молчаливого выброса (см. §2).

Малое сделано в этой ветке: обработка 409 (ротация ключа + один повтор).

## 5. Что проверить реальной тестовой заявкой (и подтвердить у Марии)

Успех фиксируется только по ответу сервиса И сообщениям Марии — отдельно
Telegram ✓/✗ и почта ✓/✗:
1. Обычная заявка с формы /preview/contact.html (имя «ТЕСТ — можно удалить»):
   экран успеха называет фактический канал(ы); в боте — заявка, на почте — копия.
2. Сценарий K-1123 (curl из отчёта PR #8: honeypot заполнен, hidden=false,
   form_started_at «сейчас»): ожидаем 201 `"delivered":{"telegram":true,…}` и
   `"flagged":["hidden-field","too-fast"]`; Мария получает заявку с пометкой
   «⚠️ Проверить на спам» — доказывает, что путь автозаполнения больше не теряет заявки.
3. Повтор после таймаута: отправить заявку дважды (второй раз — «повторить»):
   в боте НЕ должно появиться второго сообщения (duplicate:true показывает тот же номер).
4. Фикс 409: отправить заявку, поменять телефон в той же форме, отправить снова —
   заявка уходит (раньше — тупик «не получилось»).
5. Честность каналов: при живой почте и легшем Telegram текст успеха — «Мария
   увидит её в Telegram» отсутствует (проверяется только при реальном отказе канала).
